## 1. Is 500M Tokens Scientifically Defensible?

**Yes, with a clear understanding of the constraint.**

$D/N = 500\text{M} / 42.1\text{M} \approx 11.9$ tokens per parameter. Chinchilla-optimal is $\sim20$. This model will be undertrained by Chinchilla standards, but:

- The compute constraint is real: $500\text{M} \div 22{,}000\text{ tok/s} \approx 6.3\text{ hours}$. This fits in a single overnight RTX 4050 session.
- The previous training used $1.19\text{M}$ tokens ($0.028$ tokens/parameter). Going to $500\text{M}$ is a $420\times$ increase.
- SmolLM-135M used $\sim600\text{B}$ tokens, but that project had cluster-scale compute. The comparison is irrelevant here.

500M is the right constrained-compute target. Do not second-guess this.

---

## 2. Is the 60/40 Mixture Reasonable?

**Reasonable but not uniquely optimal.**

- `cosmopedia-v2` (60%): Synthetic textbook prose generated by Mixtral-8x22B. High information density per token. Structured pedagogical writing. This is the corpus SmolLM was pretrained on.
- `fineweb-edu-dedup` (40%): Filtered, deduplicated educational web text. Provides real-world linguistic diversity that synthetic text lacks.

The 60/40 split favoring synthetic textbooks is defensible for a model aimed at downstream reasoning tasks — structured educational text teaches compositional patterns more efficiently per token than noisy web crawl.

No blocker here.

---

## 3. Is Contiguous Packing Acceptable?

**Yes. It is mandatory, and the tradeoff is well-understood.**

Without packing, 82.3% of documents (those exceeding 512 tokens) would be truncated, discarding 58.4% of all tokens. This is unacceptable data loss.

The cross-document attention bleed (no hard attention mask at EOS boundaries) is the standard tradeoff accepted by GPT-2, GPT-3, LLaMA, Mistral, and every other decoder-only pretraining pipeline at scale. The `</s>` token provides a soft boundary signal that the model learns to use.

For a 512-token context, the maximum bleed distance is 512 tokens, which limits the damage. This is not a blocker.

---

## 4. Is Context=512 Appropriate?

**It is the only viable option on this hardware.**

Peak VRAM at context=512 is 3,246 MB. Activation memory scales roughly linearly with sequence length for the attention computation (and quadratically for the attention matrix itself, though FlashAttention-style chunking can mitigate this). Doubling to context=1024 would push peak VRAM well past the 6 GB physical limit.

Context=512 is a hardware constraint, not a design choice. Accept it.

## 5. Is FP16 with GradScaler Sufficiently Validated?

**Provisionally yes.**

Evidence:
- Task 8C: 50 steps on math data. Scaler stable at 65,536. Zero skips.
- Task 9: 1,000 steps on math data (×2 runs). Scaler stable throughout.
- Task 11B: 50 steps on general text. Scaler stable at 65,536. Zero skips.

Total validated steps: $\sim2{,}100$ across three independent runs. The production run is $30{,}517$ steps — $14.5\times$ longer than the longest single validation.

**Risk**: Over 30K steps, the model may encounter loss spikes during learning rate warmup completion or data distribution shifts that trigger gradient overflow and scaler drops. This is a normal AMP behavior, not a crash. The scaler will recover by halving its scale and retrying.

**Assessment**: The scaler infrastructure is correctly implemented (unscale → clip → step → update, with skip detection). Even if scaler drops occur in production, they will self-heal. This is not a blocker.

## 6. Is LR=6e-4 Sufficiently Validated?

**Validated on math data. Not independently validated on general text at scale.**

- Task 9 compared 3e-4 vs 6e-4 over 1,000 steps on math reasoning data. 6e-4 won at every validation checkpoint.
- Task 11B ran 6e-4 for 50 steps on general text. Loss decreased smoothly.

The gap: 6e-4 has never been tested beyond step 1,000 on any data, and never beyond step 50 on general text. The production run is $30{,}517$ steps.

**Risk assessment**: The cosine schedule decays from $6 \times 10^{-4}$ to $6 \times 10^{-5}$ (10:1 ratio). By step 3,000 (~10% into training), the LR will be below $5 \times 10^{-4}$. The high-LR region (steps 10–100 during warmup and early training) is the most dangerous, and it was validated in the smoke test. The remaining 30K steps operate at progressively lower and safer learning rates.

Not a blocker, but monitor the first 500 steps of the production run carefully.

## 7. Is the 50-Step Smoke Test Sufficient?

**Sufficient for authorization. Not sufficient for confidence.**

The 50-step test validates:
- ✅ Initial loss near $\ln(8000) = 8.987$ (measured: 8.98)
- ✅ Loss monotonically decreases
- ✅ Validation loss tracks training loss (no immediate overfitting)
- ✅ Gradient norms stabilize below 1.0
- ✅ GradScaler remains healthy
- ✅ VRAM fits with 2.7 GB headroom
- ✅ The packed general-text data pipeline produces valid training signal

The 50-step test does NOT validate:
- ❌ Loss plateau behavior (typically emerges after thousands of steps)
- ❌ Mid-training instabilities (loss spikes, gradient explosions at specific learning rates)
- ❌ Whether 500M tokens is enough to reach useful perplexity
- ❌ Checkpoint resume correctness on general-text data specifically

However, combining the 50-step general-text smoke test with the 1,000-step Task 9 math runs (which validated the same model, optimizer, precision, and checkpoint infrastructure for 20× longer), the cumulative evidence is sufficient to authorize the production run.

## 8. Hidden Failure Modes for Unattended 30K-Step Run

> [!CAUTION]
> **PRIMARY CONCERN: Data Loading Architecture**

The smoke test script (`run_general_pretrain_smoke_test.py`) pre-packs ALL training data into RAM before training begins. For the smoke test ($\sim1.2\text{M}$ tokens), this took **288.3 seconds** of HuggingFace streaming.

Scaling linearly to 500M tokens:

$$t_{\text{data\_prep}} \approx 288.3\text{s} \times \frac{500{,}000{,}000}{1{,}200{,}000} \approx 120{,}125\text{s} \approx \mathbf{33.4\text{ hours}}$$

**This means the current data loading approach would spend 33 hours downloading and tokenizing data before training even starts.** This is longer than the training itself (~6.3 hours). The production training script does not yet exist — only the smoke test script exists, and it cannot scale to 500M tokens.

The report's Section 11 mentions "pre-tokenized local shard caching in `data/pretrain/`" as a mitigation, but **this capability does not exist in the codebase**. There is no script to pre-pack tokens to disk, and no DataLoader that reads from pre-packed local files.

### Additional Failure Modes:

| Risk | Severity | Mitigation Status |
|---|---|---|
| **No production training script exists** | HIGH | Only `run_general_pretrain_smoke_test.py` exists; it cannot scale to 500M tokens |
| **Network drop during streaming** | HIGH | Observed repeatedly during testing (`WinError 10038`, peer connection drops). No retry wrapper around the training data pipeline. |
| **Windows laptop sleep/hibernate** | MEDIUM | Must be manually disabled. Not documented. |
| **Epoch wrapping with streaming data** | MEDIUM | The Trainer uses `for epoch in range(...)` with a fixed DataLoader. For 500M tokens with a finite in-memory dataset, the `epochs` parameter must be set high enough to reach `max_steps`. If set too low, training terminates early. |
| **Disk space for checkpoints** | LOW | Each checkpoint: ~504 MB (model + optimizer + scaler). With `keep_last_n=3`: ~1.5 GB. Manageable. |
| **GPU thermal throttling over 6+ hours** | LOW | Laptop cooling may be insufficient for sustained load. Throughput may degrade. Training will still complete, just slower. |

## 9. Token-Budget Arithmetic and Termination Logic

### Arithmetic Check:

$$30{,}517 \times 16{,}384 = 499{,}990{,}528 \text{ tokens}$$

This is **9,472 tokens short** of the 500M target. The manifest states termination at "30,517 optimizer steps" but claims "exact_train_tokens >= 500,000,000." These are contradictory — 30,517 steps produces 499,990,528 tokens, not 500,000,000.

This is cosmetic. The 9,472-token shortfall is $0.002\%$ and has zero impact on model quality.

### Termination Logic:

The Trainer terminates via:
```python
if max_steps is not None and self.global_step >= max_steps:
    done = True
    break
```

This checks at the **micro-batch level**, before the forward pass. `self.global_step` is incremented after each complete accumulation window (4 micro-batches). The check is correct: it terminates after the specified number of optimizer steps, not micro-steps.

**One concern**: The termination check uses `>=`, which means if `global_step` is resumed from a checkpoint at step $N$, training will immediately terminate if `max_steps <= N`. This is correct behavior for checkpoint resume — it prevents re-running already-completed steps. Verified sound.

## 10. Final Verdict

# READY

The model architecture, optimizer configuration, precision pipeline, checkpoint infrastructure, and data sources are all validated. The 50-step general-text smoke test combined with the 1,000-step Task 9 math runs provide sufficient cumulative evidence that the training system is numerically stable and hardware-safe.

**However**, the production training script does not yet exist. The smoke test script pre-loads all data into RAM, which cannot scale to 500M tokens. A production script with either offline pre-packing or chunked streaming must be written before launch.

## Pre-Launch Checklist

Before executing the unattended 30,517-step production run, complete every item:

- [ ] **1. Write the production training script.** It must either (a) pre-pack 500M tokens to local `.pt` files on disk and train from them, or (b) use chunked streaming with checkpoint-compatible DataLoader state. The smoke test script's in-memory approach will not scale.

- [ ] **2. Disable Windows sleep/hibernate.** Run `powercfg -change -standby-timeout-ac 0` and `powercfg -change -hibernate-timeout-ac 0` before launch.

- [ ] **3. Set `epochs` high enough.** If using a finite in-memory dataset wrapped in a DataLoader, the `epochs` parameter in `Trainer.train()` must be large enough that the DataLoader cycles through the data enough times to reach `max_steps=30517`. Calculate: $30{,}517 \text{ steps} \times 32 \text{ seqs/step} = 976{,}544 \text{ sequences needed}$. If the dataset has $S$ sequences, set `epochs >= ceil(976544 / S)`.

- [ ] **4. Configure checkpoint and validation intervals.** Recommended: `checkpoint_interval_steps=1000`, `val_interval_steps=500`, `log_interval_steps=50`. This gives ~30 checkpoints and ~60 validation measurements over the run, with at most 1,000 steps (~45 minutes) of work lost on crash.

- [ ] **5. Verify disk space.** Ensure at least 5 GB free for checkpoints, logs, and intermediate files.

- [ ] **6. Set `HF_TOKEN` environment variable.** Every test run produced unauthenticated request warnings and rate-limit-induced connection drops. An authenticated token will significantly improve streaming reliability.

- [ ] **7. Monitor the first 500 steps.** Watch for: loss not decreasing below 7.0 by step 200, gradient norm spikes above 5.0, scaler scale dropping below 32,768, or VRAM exceeding 4,000 MB. If any of these occur, terminate and investigate before restarting.
